1The Core Idea

These are not four separate projects. They are one identity system with several doors into it. The member's RFID card is the thread that ties everything together — every tap becomes a logged transaction on one member record.

Why this matters: "Who is in the building right now", "who owes what", and "who actually showed up" stop being three separate guesses and become one screen. Deactivating a single lost card kills door, court, cafe and WiFi access instantly.

4RFID — The Decisions That Matter

⚠️

An RFID card's UID is not a secret. On EM4100 (125 kHz) and MIFARE Classic cards the UID is broadcast in the clear and can be cloned in seconds with a ~$40 Flipper Zero. If "UID matches → door opens", then standing near a member for two seconds copies your building key. This is true no matter how good the software is.

Hardware decisions — lock these before you order

Card type

Use MIFARE DESFire EV3 (AES challenge–response). The card proves it holds a secret without transmitting it, so cloning means breaking AES. Costs more per card — worth it when it is also the building key.

WiFi controller

The ER605 is a gateway, not a controller. Omada captive portal needs an Omada controller — the hardware OC200, or the free Software Controller on a PC. Budget for this.

Door architecture

  • The door controller gets its own device credential and calls a server-side endpoint — it must never use the website's public key.
  • Keep lookups behind the existing get_profile_by_bracelet_uid() database function (already correctly written as SECURITY DEFINER).
  • Log every tap, including denials — who, which reader, when, allowed or refused.
  • Rate-limit the lookup (~5–10/min per source) or UIDs can be brute-forced against the door.
  • Decide fail-open vs fail-locked when the internet drops. Most small venues cache the last-known-good member list locally so entry keeps working offline.

Internet cafe WiFi portal (not built yet)

A captive-portal landing page on the F.A.E. site: the customer identifies with their RFID code, gets WiFi, and the session is billed to their wallet as a transaction. It is simply a fifth reader on the same identity system.

⚠️

Same secret problem, different door: if typing an RFID code grants internet on someone's tab, a shoulder-surfed code is a free session billed to that member. Solve it with short-lived session codes, or tap-to-authenticate at the counter rather than a typed code. Decide this during design, not after.

5Security Posture

🛡

Audited 30 Aug 2026 — no critical blockers. Row Level Security is enabled on every table and enforced at the database (not just hidden in the UI). Admin routes are gated server-side, privilege escalation via user_roles is blocked, the minors' guardian-consent flow is soundly designed, storage buckets holding payment proofs and photos are private, and no secret key has ever been committed. The .env file holds only the public anon key, which is safe by design.

Corrected finding worth remembering: an automated scan flagged the bracelets table as publicly readable. That was wrong — the policy that allowed it was created on 18 Jul and dropped on 20 Jul, and RLS denies by default. Always verify migration order chronologically before trusting a policy finding. The real leftover is a dangling GRANT SELECT … ON bracelets TO anon that was never revoked: harmless today, but it would silently open the whole bracelet directory the moment anyone adds a permissive anon policy.

7Operating Rules

📌

Edit in ONE place. The live admin site is the source of truth. Google Sheets and any local dashboard are read-only mirrors and exports. This single rule is what prevents front-desk schedule mix-ups.

  • Log incidents immediately — a logged incident is a solved incident.
  • Batch website changes — they go out together via GitHub, free.
  • Spend Lovable credits only on new AI-built features, never on edits that can be pushed.
